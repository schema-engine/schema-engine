# Docs

EcoPages docs site with EcoPages JSX MDX content and Radiant UI chrome.

The Ecopages 0.6 CLI requires Node.js 24 or newer.

## Structure

- `src/styles/` and `src/public/assets/fonts/` hold the typography tokens and self-hosted font files. The site uses IBM Plex Sans for headings and body text, IBM Plex Mono for code, and IBM Plex Serif Italic for blockquotes.
- The Layout sidebar section groups the styling guides. Recipe source tabs use the same Pierre Light+ and Dark+ highlighting as fenced blocks, and the homepage shows switchable JSON and YAML examples alongside their live form preview.
- `src/content/docs/<section>/<page>.mdx` — EcoPages JSX MDX entries with frontmatter (`title`, `description`, `order`, optional `llms`). The first folder is the sidebar section; its title, icon and position come from the typed `DOCS_SECTION_CONFIG` and `DOCS_SECTION_ORDER` in `src/content/docs.ts` (icons in `src/content/section-icons.tsx`). `test/docs-sections.test.ts` fails when a page sits outside a configured section or nests deeper than one folder. Pages may move or be deleted freely: nothing is released and the app has no redirects. Pages include Radiant and React demos. The sidebar runs Schema Engine, Registry, Actions, Forms, Forms React, Forms Radiant, Layout, then Examples; Actions documents sequential and parallel dispatch with cooperative cancellation; Examples is a set of recipes (`src/lib/examples/`), four of them framework-free: a design-system registry, a server-sent document, a checkout workflow and a server-driven workflow. Imported eco components and CSS are discovered automatically from top-level MDX imports; no `config.dependencies` block is needed. `FormRendererPreview` is a regular JSX page component (default integration, not an island): the form tree SSRs as light DOM and the base and docs layout client scripts bind its live engine after initial load and client-side navigation. React demos (`/docs/forms-react/**`, `/docs/layout/**` and `/docs/examples/**`) mount `ReactFormPreview` from `src/components/react-form-demo/` as React islands. Demo configurations live in `src/lib/form-configs/` (one module per form story) or, for a recipe, in the recipe's own `config.ts`; a page passes that object to the live previews and, with `FormConfigCode`, to the snippet, so demos and snippets cannot drift. All content is plain `.mdx`. React demos embed `ReactFormPreview` through the Ecopages JSX `EcoEmbed` plus a client hydration script, because `@ecopages/react/eco-embed` returns a React node that an Ecopages JSX file cannot render (checked on Ecopages 0.8.0). Typed in-app authoring is documented under Forms → Core concepts (Authoring modes) and Form engine setup (`defineForm` vs portable JSON). The custom-validation guide demonstrates an illustrative validator and the built-in debounced async rule; unit checks execute both snippets.
- `src/content/docs/layout/` — the Layout section, domain-neutral: overview with a quick start and the "which tool do I use" table, grid and placement, layout themes, appearance axes, theming, recipes and the recipe protocol. The registry section is an overview with a quick start, read-only and mutable registries, "Resolve a document" and the API reference; the forms engine page (`forms/builder.mdx`) lists what the engine registers and the catalog.
- `src/lib/recipes/` — the files the recipes page runs and shows: each recipe's CSS, the `tone` host axis and compiled `brandTheme`, the two engines that share it, and a custom recipe shell for React (`brand-frame.react.tsx`) and Radiant (`brand-frame.radiant.tsx`). Files import only packages (and each other with `./`), so they can be pasted into an app. `catalog.ts` lists the recipes; the configs live in `src/lib/form-configs/recipes.ts`.
- `src/components/recipe-demo/` — `RecipeDemo`: the live demo(s) of a recipe, then a tab per source. The config tab is serialized from the object the demo renders (`formConfigToCode`), the file tabs are the text of the files the demo runs (`readRecipeSource`), and a `.form.yaml` tab is written from the config with `stringifyYaml`, so a snippet cannot drift from its demo. A demo can name a Radiant engine with `data-docs-engine`; `preview-engine-binding.ts` assigns that engine on the client. The docs Radiant and React engines are both built on `brandTheme`. Recipes that use `fieldSet`, a wizard or the shared-theme engines render in Radiant only, because the React demo kit has no such elements or engines; the contact card, size tokens and custom shell render in both.
- `src/lib/examples/<recipe>/` — one folder per recipe of the Examples section (`src/content/docs/examples/<recipe>.mdx`). The files import only packages and each other with `./`, so a reader can paste the folder into an app (a recipe that is a copy of another's file, such as the registry of the server-sent document, has a test that fails when the copy differs), and the `*.test.ts` or `*.test.browser.ts` files beside them run those files. `test/examples.test.ts` fails a recipe whose page does not show a file word for word in a fence titled with the file's name (React files without their `@jsxImportSource` pragma), whose files import the docs app or another recipe, that has no test importing its files, whose page lacks an "Install" section with a `pnpm add` line naming every package the files import, or that the Examples overview does not link and list with that line. A fence titled `title="name.ts"` shows the file name above the code. The layout recipes keep the `RecipeDemo` format of `src/lib/recipes/`; the examples test lists every page that is not a folder.
- `src/lib/form-recipes/` — the files the form state pages show: the headless engine, container, issue formatter, native-facts walk-through, server-error helpers, CSRF policies, hydration and checkout wizard, the React widgets and embed, and the Radiant custom control and `FormController` element. Each is a runnable module that imports only packages and its siblings (`./engine`), and `test/form-recipe-pages.test.ts` fails when a page does not contain a file word for word (React files without their `@jsxImportSource` pragma) or a file is not listed, and when a page names `rhfAdapter` or `react-hook-form`. The headless files run in the unit project (`test/form-recipes.test.ts`), the CSRF policies and the React and Radiant files in the browser project (`src/lib/form-recipes/*.test.browser.ts`), against the built packages. `test/form-state-conformance.test.ts` checks that the Form state page shows the conformance call by the names `@schema-engine/forms/testing` exports; the suite itself runs in `packages/forms`. The browser project pre-bundles the dependencies those files reach (`browserOptimizedDeps` in `vitest.config.ts`), so a cold Vite cache does not reload a test.
- `src/public/skill/` and `src/public/skill.txt` — the agent skill the site serves, generated by `scripts/copy-skill.ts` before `dev` and `build` (and on install): the router `packages/registry/skill/SKILL.md` and every package's `skill/reference/*.md`, found by `scripts/skill-sources.ts`. They are git-ignored and replaced on every run, so do not edit them: change the skill in its package. `test/skill-sync.test.ts` keeps the router, the references and the tested examples in step.
- `src/components/action-flow/` — interactive action playgrounds on the Actions overview. Each card dispatches through `ActionDispatcher` from `@schema-engine/actions`: tap a node to run that action, or the result to run the sequence. Motion respects the visitor's reduced-motion preference.
- `src/lib/docs-nav.ts` — sidebar sections built from content entries and `DOCS_SECTION_CONFIG`, plus the flat item list used for previous and next links.
- `src/components/code-tabs` — every instance needs a unique, id-safe `name` that prefixes its tab and panel ids; the copy button shows icons and sets `data-copy-state` (`copied` or `error`), which clears with the status after 2 seconds, and failures are announced. Source tabs preserve plain-text indentation and copy the selected file verbatim; highlighted tabs retain their rendered markup and separate clipboard text.
- `src/layouts/docs-layout` — shared Radiant UI sidebar, TOC, and pagination, rendered on the server from the current route (`currentHref`).
- `src/components/docs-shell` — the client script that registers the Radiant UI elements the docs layout renders. It lives outside `layouts/` on purpose: on `@ecopages/react` 0.8.0 a bug drops bare side-effect imports from modules under a `layouts` or `pages` folder (ecopages/ecopages#1195). It can move back next to the layout once a release with the fix is installed.
- `src/pages/docs/[...slug]/index.tsx` — catch-all route for MDX content; sets the page `url` that drives the canonical link, the Markdown alternate and the Copy for LLM link.
- `src/mdx/` — MDX plugin factory (`createDocsMdxPlugins`). `rehype-pierre-code.ts` highlights every fenced block with `@pierre/highlights` (the VS Code Light+ and Dark+ pair, through `src/lib/pierre-highlight.ts`, which also serves the components that highlight as text at render time) and writes the figure: `figure[data-rehype-pretty-code-figure] > pre > code > span[data-line]` plus a sibling copy button that holds the exact source in `data-rehype-pretty-copy`, two inline SVG icons (`src/lib/copy-icons.ts`) and `data-copy-state` (`copied` or `error`). Add `showLineNumbers` after the language (` ```ts showLineNumbers `) to draw a line-number gutter; the numbers are a CSS counter, so they never reach the clipboard. An unknown language renders as plain text. The highlighter is WebAssembly, loaded when the page build runs in Node, so no code is highlighted in the browser. Build-time heading ids come from `rehype-heading-ids.ts` (same slug as `RuiToc`). The click handler lives in `layouts/base-layout/code-copy.ts`: it sets `data-copy-state` for 1.2 s, the accessible name stays "Copy code", and the result is announced through the visually hidden `role="status"` region that `BaseLayout` renders at the end of `<body>`, so it survives browser-router navigation. `styles/components/copy-button.css` draws the icon swap and honors `prefers-reduced-motion`. Callouts use `RuiAlert variant="info" layout="banner" class="unstyled"`.
- `src/lib/docs/` — `site-meta.ts` (site name, origin, canonical, OG image, sitemap extras) and `docs-llm-url.ts`; both are copied from the Ecopages docs starter, with Schema Engine values and the starter's `/docs-llm/<section>/<slug>.md` export scheme. `ECOPAGES_BASE_URL` overrides the origin.
- `src/components/form-recipe-demo/` and `src/components/renderer-tabs/` — the parts of a forms recipe page. `FormRecipeDemo` renders the recipe's config in React and in Radiant, side by side, with the docs' styled kit of each renderer (`ReactFormDemoEmbed` and `FormRendererPreview`); the recipe's own files, with their plain widgets, run in the browser tests of the recipe (`src/lib/examples/<recipe>/*.test.browser.ts`). `RendererTabs` shows one renderer's panel at a time with radio inputs and CSS only, so the files stay fenced code in the page's Markdown export. `ShadcnFormDemoEmbed` renders a form with the copied registry source instead of the demo kit; the docs page loads it by dynamic import, and only for the pages in `REACT_DEMO_PAGES` with `shadcn: true` (Forms React / Registry fields), so the engine chunk and its stylesheets reach no other page. A valid submit shows the submitted values under the form (`data-se-demo-result`). Pages that embed React demos are listed in `REACT_DEMO_SECTIONS` and `REACT_DEMO_PAGES` in `src/pages/docs/[...slug]/index.tsx`.
- `scripts/copy-registry-demo.ts` — before dev and build, copies the registry source the shadcn example renders (`input` field, `card` recipe, their primitives and styles, read from `registry.json`) into `src/generated/shadcn` with the target paths and import rewrites `shadcn add` applies (it does not run the CLI; the script's TSDoc lists the deviations): consumer aliases point at the copy and components are written as `.react.tsx`, the extension the docs' React integration owns. The copy is gitignored; `pnpm install` runs it (a `postinstall` of this package), so an editor or a bare `tsc` resolves `@/generated/shadcn` on a fresh clone. It exists because the dev client transform refuses entrypoints outside `src/`, so the demo graph cannot import `registry/` directly. `src/styles/tailwind.css` adds it as a Tailwind `@source`.
- `scripts/generate-llm-docs.ts` — writes `llms.txt` and `docs-llm/<section>/<slug>.md` into `src/public` in sidebar order, staged and swapped in only after every write succeeds. Frontmatter `llms: false` leaves a page out.

## Commands

```bash
pnpm install
pnpm dev
pnpm build
pnpm generate:llms
pnpm copy:registry-demo
pnpm check-types
pnpm test:all
pnpm test:e2e
```

`pnpm check-types` builds the site first, because the content processor writes the
`ecopages:content/*` module types during the build, then type-checks `src` and
`test`. Root `pnpm build:lib` runs it through `turbo check-types`, so it builds
the site too. Unused components that no longer type-check are excluded in `tsconfig.json`.

`pnpm test:all` runs the unit and browser projects (the unit project includes `test/styling-docs.test.ts`, which runs the snippets of the layout and registries pages, checks the documented messages against the engine and resolves every internal link and heading fragment, and `test/docs-snippets.test.ts`, which type-checks the `ts` and `tsx` fences of the docs listed in `CHECKED_DOCS`: a section, or a page of a section that is not rewritten yet. A fence that is a fragment on purpose goes in `ALLOWED_FENCES` with its reason, and a fence with `title="theme.ts"` is a file that later fences of its page can import. Tag a fence that holds JSX `tsx`) (the root pre-commit `turbo test:all` calls it). `pnpm test:e2e` builds the site, serves the production preview on a free port, and
runs Playwright checks that the contact form recipe's React demo ships its
serialized config, hydrates, keeps typed values, and surfaces validation after
submit, and that the Radiant previews on the homepage and the submit, notify and reset recipe submit, announce and reset after direct or client-side navigation, and (`styling-pages.e2e.ts`) that every styling page loads, each recipe renders and lays out as documented (in React too for the recipes that have a React demo), and every source tab copies the text it shows, and (`form-recipes.e2e.ts`) that the forms recipe pages hydrate their React demo and that an invalid submit shows errors without a reload or values in the URL, a valid submit shows the result, the wizard keeps values across steps, the renderer tabs switch panels, the copied shadcn example on Registry fields submits on one React context and client-side navigation hydrates the demos of the page that arrives. `dev-source-boundary.e2e.ts` runs the shadcn example against `ecopages dev`. Set `DOCS_E2E_BASE_URL` to test an already running server instead of
starting a preview (the site is still built first); setup fails when that server
does not answer within five seconds. Install the
browser once with `pnpm exec playwright install chromium` inside `apps/docs` if
Playwright reports a missing executable.

Open `/docs/schema-engine/introduction` after starting the dev server.

`pnpm dev` rebuilds the Radiant and React form packages before EcoPages starts.
The docs app consumes their published workspace entrypoints, so restart the dev
server after changing either package source.

React registry sources declare their JSX runtime explicitly and resolve Forms React through package exports. Keep provider and hook imports on the same package graph; source aliases in registry configuration create a second set of contexts when the app consumes built packages. For the same reason, `@schema-engine/forms-react` and its subpaths stay out of the React plugin's `runtimeModules`; the `@remarks` on the config in [eco.config.ts](./eco.config.ts) explains why.
