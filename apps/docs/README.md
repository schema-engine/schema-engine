# Docs

EcoPages docs site with EcoPages JSX MDX content and Radiant UI chrome.

The Ecopages 0.6 CLI requires Node.js 24 or newer.

## Structure

- `src/styles/` and `src/public/assets/fonts/` hold the typography tokens and self-hosted font files. The site uses IBM Plex Sans for headings and body text, IBM Plex Mono for code, and IBM Plex Serif Italic for blockquotes.
- The Layout sidebar section groups the styling guides, and its examples sit in Examples: `theming`, a form config with its theme and CSS, and `layout-page`, which has no form. Each is a folder of `src/lib/examples/`. An example page that has a stylesheet imports it from its folder, so a page loads only its own CSS. Example files are shown in fences with the same Pierre Light+ and Dark+ highlighting as the other blocks, and the homepage shows switchable JSON and YAML examples alongside their live form preview. The homepage form (`src/lib/form-configs/homepage-contact.ts`) answers a valid submit with a `show_notification` toast and a `celebrate` action, which launches confetti from the submit button of the submitted form (it does not wait for the animation, so the reset and the end of the submission are not held back) and then resets the form. `celebrate` is not built in: `createDocsDemoActions` (`src/lib/docs-demo-actions.ts`) registers it once for every docs engine, with its schema in `src/lib/docs-celebrate-action.ts`, and the document only names it. `canvas-confetti` is imported inside the action, so it is a separate chunk (`vendor-canvas-confetti-*.js`) that is not requested before the first valid submit, and never under `prefers-reduced-motion: reduce`, where the toast is still shown.
- `src/content/docs/<section>/<page>.mdx` — EcoPages JSX MDX entries with frontmatter (`title`, `description`, `order`, optional `llms`). The first folder is the sidebar section; its title, icon and position come from the typed `DOCS_SECTION_CONFIG` and `DOCS_SECTION_ORDER` in `src/content/docs.ts` (icons in `src/content/section-icons.tsx`). `test/docs-sections.test.ts` fails when a page sits outside a configured section or nests deeper than one folder. Pages may move or be deleted freely: nothing is released and the app has no redirects. Pages include Radiant and React demos. The sidebar runs Schema Engine, Registry, Actions, Forms, Forms React, Forms Radiant, Layout, Examples, then Renderer authors, the only section that documents `createFormRuntime`, the state container and the host (Write a renderer, Form runtime, State container and Native validity); Actions documents sequential and parallel dispatch with cooperative cancellation; Examples is a set of examples (`src/lib/examples/`), two of them framework-free: a server-sent document and a checkout workflow. Imported eco components and CSS are discovered automatically from top-level MDX imports; no `config.dependencies` block is needed. `FormRendererPreview` is a regular JSX page component (default integration, not an island): the form tree SSRs as light DOM and the base and docs layout client scripts bind its live engine after initial load and client-side navigation. React demos (`/docs/forms-react/**`, `/docs/layout/**` and `/docs/examples/**`) mount `ReactFormPreview` from `src/components/react-form-demo/` as React islands. Demo configurations live in `src/lib/form-configs/` (one module per form story) or, for an example, in the example's own `config.ts`; a page passes that object to the live previews and, with `FormConfigCode`, to the snippet, so demos and snippets cannot drift. All content is plain `.mdx`. React demos embed `ReactFormPreview` through the Ecopages JSX `EcoEmbed` plus a client hydration script, because `@ecopages/react/eco-embed` returns a React node that an Ecopages JSX file cannot render (checked on Ecopages 0.8.0). Typed in-app authoring is documented under Forms → Engine and registrations (`defineForm` vs portable JSON). The custom-validation guide demonstrates an illustrative validator and the built-in debounced async rule; unit checks execute both snippets.
- `src/content/docs/layout/` — the Layout section, domain-neutral: overview with a quick start and the "which tool do I use" table, grid and placement, layout themes, appearance axes, theming and the recipe protocol. `LayoutPageDemo` (`src/components/layout-page-demo/`) renders the layout page example in an iframe at a desktop width, scaled to the column, with width presets for the narrower layouts, because the theme's breakpoints are media queries of the viewport. The registry section is an overview with a quick start, read-only and mutable registries, "Resolve a document" and the API reference; the forms engine page (`forms/engine.mdx`) lists what the engine registers and the catalog.
- `src/lib/examples/<example>/` — one folder per example of the Examples section (`src/content/docs/examples/<example>.mdx`). The files import only packages and each other with `./`, and a React forms example's `<example>.react.tsx` also imports the registration barrel of the installed shadcn registry (below), so a reader can paste the folder into an app, and the `*.test.ts` or `*.test.browser.ts` files beside them run those files. `test/examples.test.ts` fails an example whose page does not show a file that is not a `*.helper.ts` helper word for word in a fence titled with the file's name (React files without their `@jsxImportSource` pragma) or shows a titled fence that is not one of its files (`shownExactly` in `test/shown-exactly.ts`, which the guide pages and the skill references use too), whose files import the docs app or another example, that has no test importing its files, whose page lacks an "Install" section with a `pnpm add` line naming every package the files import, or that the Examples overview does not link and list with that line. A fence titled `title="name.ts"` shows the file name above the code. The examples test lists every page that is not a folder, which is the overview only. The docs engines import the theme of the themed form example from its folder (`src/lib/form-engine-setup.ts`, `src/components/react-form-demo/demo-engine.ts`), and `test/shared-form-config.test.ts` checks that each demo's config is accepted by the engine it renders with.
- `src/lib/installed-components/registrations.ts` — the barrel that plays the part of the app's installed fields (`shadcn add` of the Schema Engine registry): the React examples and the settings panel of Other React state import it as `@/components/schema-engine/forms/registrations`, the path of that barrel in an app, and so their code shows the form (config, engine, renderer) and not the input, textarea, select, switch and submit components, as it does not show a package's source. The specifier is the one exception to "packages and `./` siblings": `INSTALLED_BARREL` in `test/example-format.ts` is the only non-relative, non-package import `test/examples.test.ts` accepts, the `paths` of `tsconfig.json` and the aliases of `vitest.config.ts` point it at the module, and `test/snippet-harness.ts` resolves it for the fences of the example pages and the settings panel page. The module re-exports the registrations of the copy in `src/generated/shadcn` (see `scripts/copy-registry-demo.ts` below), so it lists only the fields the docs copy; an example that needs another field adds it to the script and the barrel. A test fails an example that writes a widget of its own (`defineInput`, `defineStatic` or `useFormField`) or keeps one in a `widgets.*` file, so the widgets lesson stays on Forms React → Writing a widget. The browser tests drive the copied select through its trigger and its portalled options, since the shadcn select is not a native `<select>`.
- `src/lib/guide-sources/` — the files the guide pages show. The Renderer authors pages show the placeholder engine, `plain-renderer.ts` (a small DOM renderer built on `createFormRuntime`), the container, hydration, the runtime walk-through of a checkout and the native-facts walk-through. The app-facing Wizard page shows the checkout config with a stepper for each renderer (`useFormInstanceActions` in React, the `formInstanceContext` of `se-form-instance` in Radiant), and Form state shows a React status line. The other pages show the issue formatter, server-error helpers, CSRF policies, the React widgets and embed, and the Radiant custom control and `FormController` element. Each is a runnable module that imports only packages and its siblings (`./engine`) and, for the settings panel, the installed registration barrel, `*.helper.ts` files are the ones a page imports without showing, and `test/guide-pages.test.ts` fails when a page does not show a file word for word in a fence titled with the file's name (React files without their `@jsxImportSource` pragma), shows a titled fence that is not one of its files, or a file is not listed, and when a page names `rhfAdapter` or `react-hook-form`. The headless files run in the unit project (`test/guide-sources.test.ts`), the CSRF policies and the React and Radiant files in the browser project (`src/lib/guide-sources/*.test.browser.ts`), against the built packages. `test/form-state-conformance.test.ts` checks that the State container page shows the conformance call by the names `@schema-engine/forms/testing` exports; the suite itself runs in `packages/forms`. The browser project pre-bundles the dependencies those files reach (`browserOptimizedDeps` in `vitest.config.ts`), so a cold Vite cache does not reload a test.
- `src/public/skill/` and `src/public/skill.txt` — the agent skill the site serves, generated by `scripts/copy-skill.ts` before `dev` and `build` (and on install): the router `packages/registry/skill/SKILL.md` and every package's `skill/reference/*.md`, found by `scripts/skill-sources.ts`. They are git-ignored and replaced on every run, so do not edit them: change the skill in its package. `test/skill-sync.test.ts` keeps the router, the references and the tested examples in step.
- `src/components/action-flow/` — interactive action playgrounds on the Actions overview. Each card dispatches through `ActionDispatcher` from `@schema-engine/actions`: tap a node to run that action, or the result to run the sequence. Motion respects the visitor's reduced-motion preference.
- `src/lib/docs-nav.ts` — sidebar sections built from content entries and `DOCS_SECTION_CONFIG`, plus the flat item list used for previous and next links.
- `src/components/code-tabs` — every instance needs a unique, id-safe `name` that prefixes its tab and panel ids; the copy button shows icons and sets `data-copy-state` (`copied` or `error`), which clears with the status after 2 seconds, and failures are announced. Source tabs preserve plain-text indentation and copy the selected file verbatim; highlighted tabs retain their rendered markup and separate clipboard text.
- `src/layouts/docs-layout` — shared Radiant UI sidebar, TOC, and pagination, rendered on the server from the current route (`currentHref`). The width of the page container on a desktop, for the site header and the docs body together, is `--site-container` (90rem; running text in `.prose` keeps a 75ch measure of its own, so the extra width goes to the demos and the code) in `src/styles/theme.css`; `docs-layout.css` points Radiant UI's `--container-7xl` at it.
- `src/components/docs-shell` — the client script that registers the Radiant UI elements the docs layout renders. It lives outside `layouts/` on purpose: on `@ecopages/react` 0.8.0 a bug drops bare side-effect imports from modules under a `layouts` or `pages` folder (ecopages/ecopages#1195). It can move back next to the layout once a release with the fix is installed.
- `src/pages/docs/[...slug]/index.tsx` — catch-all route for MDX content; sets the page `url` that drives the canonical link, the Markdown alternate and the Copy for LLM link.
- `src/mdx/` — MDX plugin factory (`createDocsMdxPlugins`). `rehype-pierre-code.ts` highlights every fenced block with `@pierre/highlights` (the VS Code Light+ and Dark+ pair, through `src/lib/pierre-highlight.ts`, which also serves the components that highlight as text at render time) and writes the figure: `figure[data-rehype-pretty-code-figure] > pre > code > span[data-line]` plus a sibling copy button that holds the exact source in `data-rehype-pretty-copy`, two inline SVG icons (`src/lib/copy-icons.ts`) and `data-copy-state` (`copied` or `error`). Add `showLineNumbers` after the language (` ```ts showLineNumbers `) to draw a line-number gutter; the numbers are a CSS counter, so they never reach the clipboard. An unknown language renders as plain text. The highlighter is WebAssembly, loaded when the page build runs in Node, so no code is highlighted in the browser. Build-time heading ids come from `rehype-heading-ids.ts` (same slug as `RuiToc`). The click handler lives in `layouts/base-layout/code-copy.ts`: it sets `data-copy-state` for 1.2 s, the accessible name stays "Copy code", and the result is announced through the visually hidden `role="status"` region that `BaseLayout` renders at the end of `<body>`, so it survives browser-router navigation. `styles/components/copy-button.css` draws the icon swap and honors `prefers-reduced-motion`. Callouts use `RuiAlert variant="info" layout="banner" class="unstyled"`.
- `src/lib/docs/` — `site-meta.ts` (site name, origin, canonical, OG image, sitemap extras) and `docs-llm-url.ts`; both are copied from the Ecopages docs starter, with Schema Engine values and the starter's `/docs-llm/<section>/<slug>.md` export scheme. `ECOPAGES_BASE_URL` overrides the origin.
- `src/components/form-example-demo/` and `src/components/renderer-tabs/` — the parts of a forms example page. `FormExampleDemo` renders the example's config in React and in Radiant, filling the width of the page, with the docs' styled kit of each renderer (`ReactFormDemoEmbed` and `FormRendererPreview`); the example's own files, with the installed shadcn fields they register, run in the browser tests of the example (`src/lib/examples/<example>/*.test.browser.ts`), and the demo says so once in a note under the figures. `RendererTabs` shows one renderer's panel at a time with radio inputs and CSS only, so the files stay fenced code in the page's Markdown export. With `sideBySide` (which `FormExampleDemo` sets) its stylesheet hides the tabs and shows both panels in two columns once the tabs are 50rem wide, the room for two stages of 24.25rem each and a gap; that is a container query on the tabs, so it follows the sidebar and the table of contents and not the viewport. `ShadcnFormDemoEmbed` renders a form with the copied registry source instead of the demo kit; the docs page loads it by dynamic import, and only for the pages in `REACT_DEMO_PAGES` with `shadcn: true` (Forms React / Registry fields), so the engine chunk and its stylesheets reach no other page. A valid submit shows the notice named by the `show_notification` action of the config, in both renderers (the docs engines, the shadcn one included, register the toast of the docs shell for it). Every live form sits in the same frame, `.docs-demo-stage` (`src/styles/components/demo-stage.css`), whichever renderer draws it. Pages that embed React demos are listed in `REACT_DEMO_SECTIONS` and `REACT_DEMO_PAGES` in `src/pages/docs/[...slug]/index.tsx`.
- `src/components/theming-playground/` — the Shuffle control above the demos of the themed form example (`ThemingPlayground` wraps `FormExampleDemo`). A note in Radiant UI's inline alert style names the current picks (`describePicks`) and holds a `RuiButton` Shuffle, which draws a value of every axis (`tone`, `shape`, `font`, `size`, `surface`, read from the shared theme in `picks.ts`) and never returns the combination it started from. The picks sit in an `<output>` (role `status`) rather than a `RuiAlert`, which always stamps `role="alert"`. A shuffle only changes the `appearance` of the config (`applyPicks`: the form-level axes on the form, `size` and `surface` on the card shell); the theme and the stylesheet stay the same. `theming-playground.script.tsx` renders the new config in each renderer through its own API: for React it writes the config into the `data-se-form-config` attribute of the demo root, which `react-form-preview.client.tsx` watches and renders into the React root it already holds, and for Radiant it renders `FormRenderer` with the new config through the Radiant JSX `createRoot` into the preview, replacing the server-rendered form. The server render shows the picks of the config, so the page works without a script, and no other example page loads the component. A new config starts a new form in each renderer, so typed values are cleared by a shuffle.
- `src/components/layout-page-demo/` — the frame of the layout page example: an iframe at a desktop width (the theme's breakpoints are viewport media queries, so a desktop width is what crosses `lg`), scaled by `layout-page-demo.script.ts` to the width of the column and given the height of the page inside, with radio inputs for the Tablet and Phone widths (the widths are the `WIDTHS` list of the component, the first being the default). Without the script the frame is full size, at a fixed height, and scrolls. The frame follows the docs' light and dark mode through `color-scheme` and the system colours.
- `scripts/copy-registry-demo.ts` — before dev and build, copies the registry source the shadcn example and the examples render (the `input`, `textarea`, `select`, `switch` and `submit` fields, the `card` recipe, their primitives and styles, read from `registry.json`) into `src/generated/shadcn` with the target paths and import rewrites `shadcn add` applies (it does not run the CLI; the script's TSDoc lists the deviations): consumer aliases point at the copy and components are written as `.react.tsx`, the extension the docs' React integration owns. The copy is gitignored; `pnpm install` runs it (a `postinstall` of this package), so an editor or a bare `tsc` resolves `@/generated/shadcn` on a fresh clone. It exists because the dev client transform refuses entrypoints outside `src/`, so the demo graph cannot import `registry/` directly. `src/styles/tailwind.css` adds it as a Tailwind `@source`.
- `scripts/generate-llm-docs.ts` — writes `llms.txt` and `docs-llm/<section>/<slug>.md` into `src/public` in sidebar order, staged and swapped in only after every write succeeds. Frontmatter `llms: false` leaves a page out.

## Authoring code on a page

- A page's code shows only the API the page is about. Plumbing that the reader would not copy (fetch stubs, string building, logging harnesses, test-injection parameters such as `request = fetch`, widgets and fake services) goes in a helper that the page imports and does not show, or in a sibling file the page does show when it is part of the lesson. Do not write a stand-in inline, such as `host: { focus: () => {} }`; a test stubs the global `fetch` instead of the code taking one.
- An app-facing page uses `createFormEngine` (or `createRadiantFormEngine`) and a renderer: `FormRenderer`, the hooks or `FormController`. `createFormRuntime`, `createFormStateContainer` and hand-written hosts appear only in the Renderer authors section. A behavior that a page claims for a form (a hidden field does not submit) is shown through a renderer, and a unit test that drives the runtime keeps it covered.
- A helper is a file named `<name>.helper.ts`, or `<name>.helper.react.tsx` for React, such as `i18n.helper.ts`. The page imports it as `./i18n.helper`, so a reader sees it is a file the page leaves out. An example keeps its helpers in its folder of `src/lib/examples/`; a guide page or any other page keeps them in `src/lib/guide-sources/`, and every docs page may import them. Every other file there has to be shown word for word, so a file that is not a helper and is not shown fails `test/examples.test.ts` and `test/guide-pages.test.ts`. A helper that no source, helper, test or page imports fails too (`test/helper-files.ts` holds the convention). The runnable-page harness loads a `.ts` helper next to the titled files, and the snippet check compiles every page against all of them.

## Commands

```bash
pnpm install
pnpm dev
pnpm build
pnpm generate:llms
pnpm copy:registry-demo
pnpm check-types
pnpm test:all
pnpm test:e2e
```

`pnpm check-types` builds the site first, because the content processor writes the
`ecopages:content/*` module types during the build, then type-checks `src` and
`test`. Root `pnpm build:lib` runs it through `turbo check-types`, so it builds
the site too. Unused components that no longer type-check are excluded in `tsconfig.json`.

`pnpm test:all` runs the unit and browser projects (the unit project includes `test/docs-counts.test.ts`, which checks the validation rule count and list, the Radiant registrations and the React registry elements the pages state against the engine, the Radiant barrel and the registry source, `test/entry-points.test.ts`, which checks that the homepage and the READMEs link only to pages and files that exist, name every package and no renderer that does not exist, call an action an action, and that `llms.txt` lists the sections in the order of the sidebar, and `test/docs-contributor-content.test.ts`, which fails a user page that mentions Storybook, a repository path or the docs app, and a page or README that describes a removed API; the unit project includes `test/styling-docs.test.ts`, which runs the snippets of the layout and registries pages, checks the documented messages against the engine and resolves every internal link and heading fragment, and `test/docs-snippets.test.ts`, which type-checks the `ts` and `tsx` fences of every docs page, and `test/docs-guards.test.ts`, which fails a page outside a short list that mentions shadcn or its `@/components/` alias and any page, README or glossary that names a form library the project does not use. A fence that is a fragment on purpose goes in `ALLOWED_FENCES` with its reason, and a fence with `title="theme.ts"` is a file that later fences of its page can import. Tag a fence that holds JSX `tsx`) (the root pre-commit `turbo test:all` calls it). `pnpm test:e2e` builds the site, serves the production preview on a free port, and `test/docs-code-fences.test.ts` fails a docs page whose code fence has a line longer than 120 columns (shell fences excepted). A program that prints markup is shown in an `html` fence, formatted by `formatHtml` in `test/format-html.ts` (width 100, under a `prettier-ignore` comment), and the tests that compare a shown output with the real one format the real output with the same function.
runs Playwright checks that the contact form example's React demo ships its
serialized config, hydrates, keeps typed values, and surfaces validation after
submit, and that the Radiant previews on the homepage and the submit, notify and reset example submit, announce and reset after direct or client-side navigation, and (`homepage-celebrate.e2e.ts`) that a valid submit of the homepage form shows the toast and requests the confetti chunk only then, and never requests it under reduced motion, and that the form is reset while the confetti still falls, and (`styling-pages.e2e.ts`) that every styling page loads, the themed form example renders and lays out as documented in both renderers, and (`theming-playground.e2e.ts`) that Shuffle in the themed form playground changes the combination every time, names it in the note, and that the React and the Radiant form follow it with the same look, that the pill shape rounds the controls fully while the card keeps its corners, and that the page renders its picks without a script, and (`example-pages.e2e.ts`) that the forms example pages hydrate their React demo and that an invalid submit shows errors without a reload or values in the URL, a valid submit shows the notice, the wizard keeps values across steps, the renderer tabs switch panels, the copied shadcn example on Registry fields submits on one React context and client-side navigation hydrates the demos of the page that arrives. `dev-source-boundary.e2e.ts` runs the shadcn example against `ecopages dev`. starting a preview (the site is still built first); setup fails when that server
does not answer within five seconds. Install the

Playwright reports a missing executable.

Open `/docs/schema-engine/introduction` after starting the dev server.

`pnpm dev` rebuilds the Radiant and React form packages before EcoPages starts.
The docs app consumes their published workspace entrypoints, so restart the dev
server after changing either package source.

React registry sources declare their JSX runtime explicitly and resolve Forms React through package exports. Keep provider and hook imports on the same package graph; source aliases in registry configuration create a second set of contexts when the app consumes built packages. For the same reason, `@schema-engine/forms-react` and its subpaths stay out of the React plugin's `runtimeModules`; the `@remarks` on the config in [eco.config.ts](./eco.config.ts) explains why.
