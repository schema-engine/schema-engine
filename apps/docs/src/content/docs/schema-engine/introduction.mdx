# Schema Engine

Schema Engine is a common language for describing interfaces as data. You register the pieces an interface is made of, describe a screen or a process as a JSON document that names those pieces, and let a renderer draw it. The document can be written by hand, stored, or built on a server and sent to a client, and it stays the same data everywhere.

## Why it exists

Schema Engine comes from years of building forms and from seeing most of the ways to build them. Complex forms are hard to represent: fields that depend on other fields, steps that depend on earlier answers, checks that call a server, work that runs after a submit. After a lot of trial and error the result was a structure that holds them, and Schema Engine is that structure.

Two things mattered from the start. The person who builds with it owns the result: their inputs, their decorative elements, their design system. And it does not bend to a library or a framework. Schema Engine is not a component kit. It is a small set of rules, a common ground that anyone can use to describe their own interface and their own way of working, and that every renderer reads the same way.

## The common language

Four ideas carry everything else. [Core concepts](/docs/schema-engine/core-concepts) defines each term once.

**Registry.** A registry is a collection of registrations that follow the same rules. Each registration has a `$type`, a schema for its configuration and metadata: your text input, your card, your analytics call. A document names registrations by `$type`. The registry resolves each one, and its schema validates the configuration. Registering stays simple, and it is not limited to forms. See [Registry](/docs/registry/overview).

**Actions.** An action is registered behaviour. You define it once in code, on the client. An action entry in a document is plain data: its `$type`, its arguments and the triggers it answers. Entries run in order, a nested list runs in parallel, and an action that fails can stop the rest and cancel its siblings. An async workflow is therefore a JSON array you can store, send and replay, and `parseActions` checks every entry against its registration before anything runs. See [Actions](/docs/actions/overview).

**Serialized documents.** Everything a document holds is JSON: no functions, no class instances, no framework objects. That is what lets a server send an interface to a client, a CMS store it or a tool generate it, and what lets the engine check it, at the boundary, against the schemas your registrations declare. YAML works too. See [Serialized documents](/docs/schema-engine/serialized-documents).

**Rendering from data.** A renderer takes a validated document and draws it with the registrations of its domain's engine, the object that holds that domain's registries. The rules for resolving, validating and dispatching live in the engine, not in the renderer, so a document keeps its meaning from one renderer to the next.

## Domains

A domain gives the language a job. **Forms** is the first. It adds fields, validation rules, constraints, steps, the form state and the submit lifecycle, and it renders with [Forms React](/docs/forms-react/overview) or [Forms Radiant](/docs/forms-radiant/overview). [Layout](/docs/layout/overview) is not a domain: it is domain-neutral, with a grid, named appearance and the recipe protocol a domain uses for the frame around its content. See [Forms](/docs/forms/overview).

## What you own

You own your vocabulary: the components and actions you register, usually your design system. Schema Engine ships reference components to start from, as React source you copy into your app and as Radiant elements in the package. Change them or replace them. Registrations accept any [Standard Schema](https://standardschema.dev/) validator, such as Zod, Valibot or Effect Schema.
