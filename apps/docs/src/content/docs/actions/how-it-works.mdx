# How Actions Work

This page explains the generic lifecycle of the actions package.

Forms is the first concrete consumer in this repo, but the mechanics below are package-level behavior.

## Lifecycle

1. Register action types in an `ActionRegistry`.
2. Provide action configs to the executor.
3. Trigger execution with a trigger value and base context.
4. The executor resolves matching registrations.
5. The executor enriches the provided context with `config` and `trigger`.
6. Actions run sequentially and return normalized results.

## Registration Example

```typescript
const registration = {
	$type: 'log',
	schema: LogActionSchema,
	metadata: {
		name: 'Log Action',
		defaultTriggers: ['submit'],
	},
	execute: async (context) => {
		console.log(context.trigger, context.config.message);
		return { success: true };
	},
};
```

## Trigger Matching

The executor checks action configs in order.

- If the config has a `triggers` array, that list is used.
- Otherwise the registration `metadata.defaultTriggers` is used.

## Context Enrichment

The key runtime behavior is this merge:

```typescript
execute({
	...context,
	config: action,
	trigger,
});
```

That is why actions usually read `context.config` and `context.trigger` directly.

## Execution Order

Actions run in array order, not registry registration order.

```typescript
await executor.execute({
	actions: [
		{ id: 'a', $type: 'log', message: 'first' },
		{ id: 'b', $type: 'log', message: 'second' },
	],
	trigger: 'submit',
	context,
});
```

## Control Flow

An action result can stop the chain:

```typescript
return {
	success: false,
	error: 'Stop here',
	shouldContinue: false,
};
```

## Downstream Implementations

The forms package builds on this model by defining a richer execution context with form-specific fields such as `formData`, `errors`, and controller methods. That is an implementation built on top of the generic action primitives, not behavior built into this package.
