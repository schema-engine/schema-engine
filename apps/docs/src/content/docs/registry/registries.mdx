# Read-only and mutable registries

Everything a Schema Engine package lets you extend is a registration in a registry: an element, a recipe, an action, an appearance axis, a validation rule. They all share one shape and one mechanism, so overriding a default works the same way for each. A registry is built as read-only from a list, or as mutable when registrations arrive at runtime.

## Read-only or mutable

| Question                      | `createRegistry`                                                                                     | `createMutableRegistry`                                              |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| When are registrations known? | At build, from a list                                                                                | Any time, after construction                                         |
| Can it change?                | No. It is frozen, with no `register` or `clear`                                                      | Yes: `register`, `clear`                                             |
| A second `$type` of one key   | Replaces the first silently (or throws with `duplicates: 'error'`); the key keeps its first position | The same: replaces it silently, or throws with `duplicates: 'error'` |
| Is the schema checked?        | Yes, for each winner, at build                                                                       | Yes, at each `register`                                              |
| Use it for                    | Elements, recipes, actions, axes and validations of an engine                                        | A plugin system that registers at runtime                            |

Both return the same read side (`get`, `has`, `all`, `keys`, `size`, `kind`), so either goes wherever a registry is read. `createRegistry` is the default. Reach for `createMutableRegistry` only when registrations arrive after the registry exists; the forms engine never does.

```ts
import * as z from 'zod/mini';
import { createRegistry } from '@schema-engine/registry';
import type { BaseRegistration } from '@schema-engine/registry';

const defaults: BaseRegistration[] = [
	{ $type: 'card', schema: z.object({ title: z.string() }), metadata: { name: 'Card' } },
];
const custom: BaseRegistration = {
	$type: 'card',
	schema: z.object({ title: z.string(), tone: z.string() }),
	metadata: { name: 'Tonal card' },
};

export const widgets = createRegistry('Widget', [...defaults, custom]);

export const name = widgets.get('card')?.metadata.name; // 'Tonal card': last wins
```

Where a repeated `$type` is always a mistake, such as the component keys of a catalog, pass `{ duplicates: 'error' }` and the build throws `Widget 'card' is registered twice.` instead of replacing the first registration. The default, `'override'`, is what `[...defaults, custom]` relies on.

```ts
import * as z from 'zod/mini';
import { createRegistry } from '@schema-engine/registry';
import type { BaseRegistration } from '@schema-engine/registry';

const card: BaseRegistration = { $type: 'card', schema: z.object({ title: z.string() }), metadata: { name: 'Card' } };

export function build() {
	// Throws: Widget 'card' is registered twice.
	return createRegistry('Widget', [card, card], { duplicates: 'error' });
}
```

Each winning `schema` must be a Standard Schema, so any provider works. A value without `~standard.validate` throws at build and names the registry and the key: `Widget 'card' schema must implement Standard Schema (~standard.validate).` An overridden registration is not checked.

## One contract, a binding per renderer

When one set of `$type`s is drawn by several renderers, define each `$type` and its schema once as a registry of contracts, and let each renderer add only its part with `bindRegistry`. The schema is shared by identity, and a renderer that forgets a `$type` fails to compile.

```ts
import * as z from 'zod/mini';
import { bindRegistry, createRegistry } from '@schema-engine/registry';
import type { RegistryBindings } from '@schema-engine/registry';

const contracts = createRegistry('Widget', [
	{ $type: 'card', schema: z.object({ title: z.string() }), metadata: { name: 'Card' } },
	{ $type: 'badge', schema: z.object({ label: z.string() }), metadata: { name: 'Badge' } },
]);

interface ReactBinding {
	render: (props: never) => string;
}

export const reactWidgets = bindRegistry(contracts, {
	card: { render: (props: { title: string }) => `<h1>${props.title}</h1>` },
	badge: { render: (props: { label: string }) => `<b>${props.label}</b>` },
} satisfies RegistryBindings<typeof contracts, ReactBinding>);

export const radiantWidgets = bindRegistry(contracts, {
	card: { tag: 'se-card' },
	badge: { tag: 'se-badge' },
});

export const sameSchema = reactWidgets.get('card').schema === radiantWidgets.get('card').schema; // true
export const tag = radiantWidgets.get('badge').tag; // 'se-badge'
```

Leave out `badge`, add a `crad` key or set `schema` in a binding and TypeScript refuses it. With contracts typed only as `BaseRegistration`, the build throws instead and names the registry and the key: `Widget 'badge' has no binding.` See the [API reference](/docs/registry/api-reference#bindregistry).

## The mutable registry

Use `createMutableRegistry` when plugins register themselves after startup:

```ts
import * as z from 'zod/mini';
import { createMutableRegistry } from '@schema-engine/registry';
import type { BaseRegistration } from '@schema-engine/registry';

interface PluginRegistration extends BaseRegistration {
	execute: () => Promise<void>;
}

const plugins = createMutableRegistry<PluginRegistration>('Plugin');

plugins.register({
	$type: 'sync-cache',
	schema: z.strictObject({ enabled: z.boolean() }),
	metadata: { name: 'Sync cache' },
	execute: async () => {},
});
```

`register` checks each registration as `createRegistry` does and throws a `RegistryError` for a schema that is not a Standard Schema or for malformed `childPaths`. It logs nothing on an override: call `plugins.has('sync-cache')` first to warn about one. The actions package takes either kind: `parseActions` and `ActionDispatcher` read any registry, so `createRegistry('Action', [...])` builds a fixed set and `createMutableRegistry<MyAction>('Action')` takes actions at runtime.

See the [API reference](/docs/registry/api-reference) for every member.
