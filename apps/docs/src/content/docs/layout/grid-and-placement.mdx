# Grid and placement

## Placing fields in the grid

A form's `grid` sets its layout (`columns`, `gap`, `responsive`), and each
element's own `grid` places it. There are three levels, from the most to the
least readable:

1. `width` and `offset` for fields that flow in rows.
2. `areas` for a layout you draw as rows of names.
3. Raw grid lines (`column`, `row`) as the escape hatch.

A grid uses either `width`/`offset`, `areas` or `columns`; raw lines can sit
next to widths or areas.

### Rows of fields: `width` and `offset`

For the common layouts, name the width:

```ts
export const fields = [
	{ $type: 'input', id: 'first', name: 'first', grid: { width: 'half' } },
	{ $type: 'input', id: 'last', name: 'last', grid: { width: 'half' } },
	{ $type: 'input', id: 'bio', name: 'bio', grid: { width: 'half', offset: 'quarter' } },
];
```

`width` is `full`, `three-quarters`, `two-thirds`, `half`, `third`, or
`quarter`. `offset` leaves empty space before the field and takes the same names
except `full`, so `half` with a `quarter` offset is centred in its row. A width
on its own is the share of the row the field takes; the grid decides where it
lands, so two `half` fields share a row. Leave the width out for a field that
fills the row.

Both change by breakpoint through the element's `grid.responsive`, like every
other placement key. A slot that sets only the width keeps the offset of the
slot before it, and the other way round:

```ts
export const field = { grid: { width: 'full', responsive: { md: { width: 'third' } } } };
```

A grid whose fields use `width` or `offset` is laid out on 12 tracks, so each
name is a whole number of tracks (`half` is 6, `third` is 4, `quarter` is 3), and
a field in that grid that sets no width fills the row. Fieldsets and array rows
lay out their children on their own grid, so `width` and `offset` work on a
container's children the same way, and the enclosing grid's `columns` do not conflict
with them.

Validation enforces these rules for named widths:

- A form grid that sets `columns` or `minColumnWidth` (at any breakpoint) cannot
  contain a top-level field that uses `width` or `offset`: a grid uses areas,
  widths or columns.
- A field that sets `width` or `offset` cannot also set a raw `column`.
- A field's `offset` plus `width` must fit in 12 tracks, counting the value
  each carries from a narrower breakpoint: `two-thirds` after a `half` offset
  is rejected.

### Drawn layouts: `areas`

When a field spans several rows or columns next to stacked fields, `width` and
`offset` cannot say it. Draw the layout instead: the grid's `areas` is a list
of rows, each row lists area names separated by spaces, and `.` is an empty
cell. A field claims a name with `grid.area`.

```yaml
grid:
    areas:
        default: ['a', 'b', 'c', 'd', 'e']
        md:
            - 'a a a b b b'
            - 'a a a c c c'
            - 'd d e e e e'
elements:
    - { $type: input, id: a, name: a, grid: { area: a } }
    - { $type: input, id: b, name: b, grid: { area: b } }
    # c, d and e claim their own area the same way
```

Below `md` the five fields stack. From `md`, `a` spans three columns and two
rows, `b` and `c` stack beside it, and `d` and `e` share the last row. The
column count comes from the rows, so a grid with `areas` sets no `columns`.
`areas` is an array for one layout at every width, or a record keyed `default`,
`sm`, `md`, `lg`, `xl` and `2xl` (a slot you leave out keeps the layout of the
slot before it). A responsive record must include `default`. A field's `area`
is also responsive through `grid.responsive`, so a field can claim a different
area when the template changes.

A few things the template does not police:

- A field with no `area` in an areas grid is auto-placed: it fills a `.` cell
  if one is free, otherwise it opens an implicit row after the drawn ones. A raw
  `column` or `row` on such a field works as it does anywhere else.
- Two fields may claim the same area. That is meant for fields that are never
  shown together (constraints, or `hidden` at a breakpoint); if both show, they
  are drawn over the same cells.
- A field hidden at a breakpoint (`grid.responsive.<slot>.hidden`) need not be in
  that breakpoint's template, and the hidden state carries to wider
  breakpoints until a slot shows it again.
- A step with no fields under a form-level `areas` needs `grid: {}` from the
  author: an empty grid of its own that replaces the form's. Without it, every
  template area counts as unclaimed on that step and validation rejects it.

A step takes its own `grid`, which replaces the form's grid for that step. An
areas template names specific fields, so each wizard step draws its own: the
address step below has its own template, and the payment step keeps the form's
two columns. A form-level `areas` would apply to every step without a `grid` of
its own, and each of those steps would then have to claim every area in it:

```ts
import { engine } from './engine';

export const checkout = engine.defineForm({
	id: 'checkout',
	grid: { columns: 2 },
	steps: [
		{
			id: 'address',
			title: 'Address',
			grid: { areas: ['street street', 'city zip'] },
			elements: [
				{ $type: 'input', id: 'street', name: 'street', grid: { area: 'street' } },
				{ $type: 'input', id: 'city', name: 'city', grid: { area: 'city' } },
				{ $type: 'input', id: 'zip', name: 'zip', grid: { area: 'zip' } },
			],
		},
		{ id: 'payment', title: 'Payment', elements: [] },
	],
});
```

Validation names the path of whatever it rejects:

- Rows of one template must have the same number of cells, and each name's cells
  must form a rectangle. CSS drops a whole template that breaks either rule.
- Every field `area` must be in the template at each breakpoint where the grid
  draws one, and every area in the template must be claimed by a field.
- `areas` cannot be mixed with `columns` or `minColumnWidth`, or with `width` or
  `offset` on the grid's fields: a grid uses areas, widths or columns.
- A field cannot set `area` together with `width`, `offset`, `column` or `row`.
- Names are ASCII CSS identifiers (`street`, `side-2`) and cannot be `auto`,
  `span`, `none`, `default`, `inherit`, `initial`, `unset`, `revert` or
  `revert-layer`. A name is written into a CSS custom property, so anything
  that is not an identifier is rejected.
- Fieldsets and array rows lay their children out without `areas`, so `area` is
  rejected on a container's children. Use `width` and `offset` there.

### Raw grid lines

Raw `column`, `row` and `placeSelf` stay available as the escape hatch for
anything the names do not cover. `column: 2` is a CSS grid line, not a span:
it starts the field at line 2. Use `column: 'span 2'` to span two columns, or
`column: '4 / 10'` for explicit lines. A raw `column` field may sit next to
width fields, but it counts tracks of the 12 the widths use there, so
`column: 'span 2'` is two of twelve, a sixth of the row.

## The layout theme and appearance

The grid vocabulary (breakpoint thresholds, gap tokens, the default minimum column
width) and the appearance axes (`size` and `surface` built in, plus any you define)
belong to one **layout theme**, compiled by `@schema-engine/layout` and passed to the
engine as `layout`, either compiled once or as inline `{ grid, appearance }` options:

```ts
import { createFormEngine } from '@schema-engine/forms';
import { createLayoutTheme } from '@schema-engine/layout';
import { elements } from './registrations';

const theme = createLayoutTheme({ grid: { breakpoints: { md: '50rem' } } });

const checkout = createFormEngine({ elements, layout: theme });
const profile = createFormEngine({ elements, layout: theme });
```

Engines built on one compiled theme carry the same `data-se-theme` and the same stylesheet
content; [Layout themes](/docs/layout/layout-themes#share-a-theme-between-engines) says how each renderer emits it. A form of one engine can sit inside a grid item of another: the nearest
theme's token rules apply.

A form, a step, a field or a recipe slot picks a named value per axis with
`appearance: { size: 'compact' }`, and the renderer writes `data-se-size="compact"`.
A registration declares the axes it responds to with `appearanceAxes`, and `validateForm`
rejects a pick on any other axis, an unknown axis and an unknown value.

The full guides are in [Layout](/docs/layout/overview):

- [Appearance axes](/docs/layout/appearance-axes): the definition, what makes a good axis, `size` and `surface`, `defineAxis` and host axes.
- [Theming](/docs/layout/theming): the custom properties a host overrides.
