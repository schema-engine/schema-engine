# Core Concepts

Schema Engine separates serializable form data from framework rendering. The
core package registers elements, view recipes, and actions; an adapter renders
the selected recipe.

## Authoring modes

Choose how you author form configuration based on where the data lives:

| Mode                       | Use when                                          | API                                                                |
| -------------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| **TypeScript in your app** | The form is hardcoded next to a known engine      | `engine.defineForm({ ... })` — full typing from your registrations |
| **Portable JSON**          | CMS, API, storage, or shared files across systems | Plain `FormConfig` (or raw JSON) + `engine.validateForm(unknown)`  |

`defineForm` and `validateForm` run the same validation pipeline. `defineForm`
only adds compile-time checks for the engine you built. The exported `FormConfig`
type is envelope-level: it does not narrow each `$type` until validation runs.

Both throw a `FormValidationError` on an invalid form. `engine.safeValidateForm(json)`
returns `{ success, data | issues }` instead, and each issue carries the config `path`
it is about (see [Form configuration errors](#form-configuration-errors)).

With `FormRenderer`, passing a plain config is enough — the renderer calls
`validateForm` at the form boundary. Pre-validate only when you need a
`NormalizedFormConfig` outside the renderer (caching, tests, custom pipelines).

## Form configuration errors

Validation errors are about a field's _value_. A form's _configuration_ (a width that does not exist, a
recipe that is not registered, a rule with no handler) is checked by `engine.validateForm`, which throws a
`FormValidationError` listing the problems it found. Each issue has a `message` and the `path` of the config key it
is about, so you can point at the mistake without parsing English:

| Problem                                           | `path`                                                            |
| ------------------------------------------------- | ----------------------------------------------------------------- |
| The third field of step 1 has `grid.width: halve` | `['steps', 0, 'elements', 2, 'grid', 'width']`                    |
| A fieldset child uses a rule with no handler      | `['steps', 0, 'elements', 1, 'elements', 0, 'rules', 0, '$type']` |
| `view.$type` is not a registered recipe           | `['view', '$type']`                                               |
| A problem with the whole form                     | `[]`                                                              |

`error.message` has one line per issue, `<path>: <message>`, with array indexes in brackets and the `id` of each
element or step the path passes:

```text
steps[0] (contact).elements[2] (email).grid.width: Expected one of full, three-quarters, two-thirds, half, third, quarter.
view.$type: Unknown view recipe 'nope'. Register it with createFormEngine({ recipes: [...] }).
```

An issue a schema reported also has a `code` and `params` (for example `too_small` with `{ minimum: 3 }`), so
an editor can localize the diagnostic instead of showing the English `message`. An issue the engine finds
itself has neither. A union that fails is reported at the key that failed in the branch the value was closest
to, or at the union when no branch is.

A malformed form envelope (its own shape, such as `steps` not being an array) stops the deeper checks and is
reported alone. An unrecognized key is reported at the key itself, for example `['view', 'shell', 'bogus']`.

Use `engine.safeValidateForm` when you would rather branch on a result than catch:

```ts
import { formatIssuePath } from '@schema-engine/forms';
import { engine } from './engine';

export function loadForm(json: unknown) {
	const result = engine.safeValidateForm(json);
	if (!result.success) {
		for (const { path, message } of result.issues) {
			console.error(`${formatIssuePath(path) || '(form)'}: ${message}`);
		}
		return undefined;
	}
	return result.data; // the same frozen NormalizedFormConfig validateForm returns
}
```

The `{ message, path }` shape is a Standard Schema issue, so a YAML loader or an editor can map each `path` to
a line or a field. `FormRenderer` and the Radiant provider call `validateForm`, so an invalid config thrown at
render time shows the same lines in the error message.

## Registration

```ts
import { createFormEngine, SubmitActionRegistration } from '@schema-engine/forms';
import { text } from './registrations';

export const engine = createFormEngine({
	elements: [text],
	actions: [SubmitActionRegistration],
});
```

The registrations are the ones the [quick start](/docs/forms/getting-started) writes. A form that names a `$type` the engine has not registered fails `validateForm`, and a form that names the `submit` action fails the same way until `SubmitActionRegistration` is registered.

Each list is stored in a read-only registry: a later `$type` replaces an earlier one, and a
schema that is not a Standard Schema fails the build. `validations` adds custom rules and
`layout` sets the [layout theme](/docs/layout/grid-and-placement#the-layout-theme-and-appearance); see
[What the forms engine registers](/docs/forms/builder#what-the-forms-engine-registers).

## Form configuration

```ts
import { createRadiantFormEngine, schemaFormRegistrations } from '@schema-engine/forms-radiant';

const engine = createRadiantFormEngine({ elements: schemaFormRegistrations });

export const config = engine.defineForm({
	id: 'contact',
	title: 'Contact',
	steps: [{ id: 'details', title: 'Details', elements: [] }],
	view: {
		$type: 'card',
		shell: { appearance: { size: 'default' } },
		header: { showDescription: true },
	},
});
```

This engine comes from a renderer package, which registers the recipes it ships. `view.$type` selects one registered recipe. The recipe determines its kind and
allowed slots. Single-step recipes require exactly one step; wizard recipes
require at least two. A single-step form may omit `view` to render fields
directly.

`validateForm` / `defineForm` parse the form schema and, when `view` is present,
validate the registered recipe's kind and slot config. Nested child elements are
validated at the same boundary; the normalized marker is applied only after that
succeeds. They return a frozen `NormalizedFormConfig` owned by that engine.
Snapshot isolation copies plain objects and arrays; other objects currently
remain shared. A form normalized by one engine cannot be passed to another;
start from authoring input or JSON instead. They write the resolved `view`:
a multi-step form that omits `view` gets `{ $type: 'bare-controls' }` (or the
engine's `defaultWizardRecipe`), and each slot config is the recipe's
`slotDefaults` under the author's keys, merged deep. When the default recipe is
not registered the form validates without a `view`, `validateForm` warns, and
the renderer paints fields without chrome. Renderers read the normalized `view`
and do not apply defaults themselves.

A multi-step form is a wizard. A step may take `constraints` (`show` or `hide`, on non-row fields of earlier steps; the
first step has none) and is skipped when they hide it, and the form's `navigation` is `'linear'` (default) or `'free'`.
Both renderers run the wizard, the submission and every action through one form runtime (`createFormRuntime`), so
step ids, skipped steps, submit as Next and the reset rule behave the same in React and Radiant.

React and Radiant render that normalized form. They do not re-parse element
input schemas. A field created outside a form must go through
`engine.validateElement()` first.

Authors supply schema **input**; defaulted properties stay optional in
`defineForm`. Components receive schema **output**. Nested fieldset and array
children are typed from the same engine registrations as top-level fields.
Containers render those children with `FormElements` and a field scope instead
of cloning configuration to change paths.
